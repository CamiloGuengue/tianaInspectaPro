# Justificación arquitectónica

## 1. Qué datos viven en SQL y por qué

En SQL almacenamos el **estado oficial del negocio (source of truth)**: información transaccional que requiere consistencia fuerte y trazabilidad histórica.

### Datos
- Usuarios
- Conductores
- Vehículos
- Servicios solicitados
- Asignación conductor-servicio
- Pagos
- Estados del servicio (creado, aceptado, iniciado, finalizado, cancelado)
- Calificaciones finales

### Por qué

Este tipo de información define obligaciones reales entre partes.

Necesitamos:

**Consistencia fuerte (ACID)**  
No pueden existir:
- dos conductores en el mismo servicio
- un pago sin servicio
- un servicio finalizado sin inicio
- un usuario eliminado con servicios activos

**Integridad referencial**

Relaciones obligatorias:

Servicio → pertenece a Usuario  
Servicio → pertenece a Conductor  
Pago → pertenece a Servicio

**Trazabilidad legal**

El historial no puede cambiar retroactivamente.  
Es evidencia operativa y financiera.

SQL se usa porque el negocio depende de que estos datos sean correctos.

---

## 2. Qué datos viven en NoSQL y por qué

En NoSQL almacenamos **actividad operacional de alta frecuencia**: datos masivos, volátiles o no críticos para la validez legal del sistema.

### Datos
- Ubicación en tiempo real del conductor (stream GPS)
- Historial de posiciones
- Notificaciones
- Sesiones activas
- Estados efímeros (online/offline, escribiendo, en camino)
- Logs de interacción
- Métricas de uso

### Por qué

Estas propiedades requieren:

**Alta escritura**  
Ubicación cada 1–3 segundos por conductor.

**Estructura variable**  
Distintos dispositivos envían diferentes campos.

**Tolerancia a pérdida**  
Perder una posición no invalida el negocio.

**Acceso por clave, no relacional**

Consultas típicas:

driverId → últimas posiciones  
userId → notificaciones

NoSQL optimiza throughput y latencia, no consistencia estricta.

---

## 3. Riesgos de un modelo completamente relacional

Si todo fuera SQL:

### Problemas de rendimiento
- Millones de inserts por ubicación saturan índices
- Locks de escritura bloquean transacciones críticas
- Aumenta latencia en pagos y asignaciones

### Contaminación del dominio
Datos efímeros mezclados con datos legales → mantenimiento complejo

### Escalabilidad costosa
Escalar verticalmente la base transaccional es caro y limitado

**Resultado:** el sistema crítico se vuelve lento por datos no críticos.

---

## 4. Riesgos de un modelo completamente documental

Si todo fuera NoSQL:

### Inconsistencia del negocio
Podrían existir:
- pagos duplicados
- doble asignación de conductor
- servicios huérfanos

### Falta de integridad referencial
No hay garantía automática de relaciones válidas.

### Problemas financieros y legales
No hay transacciones confiables multi-documento.

**Resultado:** sistema rápido pero incorrecto.

---

## 5. Cómo están conectados ambos modelos

Arquitectura: **SQL = estado / NoSQL = eventos**

### Flujo

1. Usuario solicita servicio → SQL crea servicio
2. Conductores envían ubicación → NoSQL
3. Sistema selecciona conductor usando NoSQL
4. Confirmación → SQL asigna conductor (transacción)
5. Durante viaje → tracking en NoSQL
6. Finalización → SQL cierra servicio y genera pago

El ID del servicio generado en SQL se usa como referencia en NoSQL.

---

## 6. Consistencia y trazabilidad

Modelo aplicado: **Consistency at write boundaries**

- Lo legal se confirma solo en SQL
- Lo operativo vive en NoSQL
- Eventos NoSQL nunca modifican la verdad directamente
- Solo disparan decisiones que luego se confirman en SQL

> NoSQL propone — SQL decide

---

## 7. Cómo el negocio influye en el diseño

El sistema coordina servicios reales entre personas.

Existen dos realidades:

**Realidad contractual**  
Debe ser exacta → SQL

**Realidad operacional en tiempo real**  
Debe ser rápida → NoSQL

La arquitectura se define por la naturaleza del negocio:  
servicios físicos en tiempo real con implicaciones económicas.

---

## Conclusión

Usamos una arquitectura híbrida porque el sistema tiene dos tipos de verdad:

- verdad legal → SQL
- verdad operacional → NoSQL

Separarlas permite simultáneamente:

- corrección
- escalabilidad
- baja latencia

Un solo modelo no puede optimizar las tres a la vez.
